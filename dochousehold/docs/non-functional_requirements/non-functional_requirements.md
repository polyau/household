В данном разделе описываются нефункциональные требования к MVP.

:::note
Приоритеты указаны по MoSCoW:<br />Must - критично для MVP, без этого нельзя запускать продукт;<br />Should - важно для MVP, сильно влияет на качество продукта и бизнес-метрики;<br />Could - желательно для MVP, лучше реализовать при наличии ресурсов.
:::

|ID|Категория|Название|Описание требования|Прио-ритет|Обоснование|
|-|-|-|-|-|-|
|NFR-01|Безопасность|Защищённая передача данных|Все запросы между приложением и сервером выполняются только по HTTPS/TLS; незашифрованные соединения не допускаются.|Must|**Риск:** перехват/подмена данных, доступ к содержимому чужих пространств.<br />**Последствия:** утечка данных - потеря доверия, репутационные и юридические риски.|
|NFR-02|Безопасность|Хранение и защита паролей|Пароли хранятся только в виде хеша; после 5 неудачных попыток входа - блокировка на 15 минут.|Must|**Риск:** подбор пароля и захват аккаунта.<br />**Последствия:** доступ злоумышленника к данным пространств и их пользователей, возможность вредоносных изменений - конфликты внутри пространства + утечка ПД.<br />**Логика:** 5 попыток + временная блокировка снижают эффективность подбора без усложнения UX для обычного пользователя.|
|NFR-03|Безопасность|Разграничение доступа по пространствам и ролям|Пользователь имеет доступ только к данным тех пространств, где где он состоит; операции управления приглашениями доступны только администратору пространства.|Must|**Риск:** доступ к чужим данным из-за ошибки авторизации/проверки прав.<br />**Последствия:** потеря доверия, конфликтные ситуации, юридические последствия (данные о быте/планах относятся к ПД/частной информации).<br />**Комментарий:** модель "пространства" - основа продукта; нарушение границ делает продукт непригодным.|
|NFR-04|Нормативно-правовые|Персональные данные и информирование пользователя|Продукт должен обеспечивать соблюдение требований по обработке ПД (152-ФЗ): пользователю предоставляются политика обработки данных и пользовательское соглашение; фиксируется факт ознакомления/согласия при регистрации.|Must|**Риск:** несоблюдение требований по ПД.<br />**Последствия:** претензии/жалобы пользователей, юридические риски и необходимость срочно переделывать процессы обработки данных.|
|NFR-05|Производительность|Время отклика запросов API|Среднее время отклика на ключевые запросы максимум 500 мс.|Must|**Риск:** при задержках интерфейс воспринимается как “тормозящий”, пользователи уходят.<br />**Последствия:** провал активации/удержания.<br />**Комментарий:** удобное использование предполагает быстроту работы приложения.|
|NFR-06|Производительность|Загрузка основных экранов|Время загрузки экранов "Задачи", "Покупки" "Календарь" меньше 2 с для 95% открытий при стабильном интернет-соединении.|Should|**Данные:** Google считают 2 с для p95 типовой границей восприятия "быстро/медленно" в пользовательском опыте.<br />**Риск:** если экраны регулярно грузятся долго, у пользователя пропадает желание пользоваться приложением.<br />**Последствия:** падение активности и retention.|
|NFR-07|Надёжность|Доступность сервиса|Доступность сервиса ≥ 99% в месяц.|Must|**Риск:** недоступность сервиса ломает бытовые процессы.<br />**Последствия:** пользователи теряют доверие и возвращаются к альтернативам, которые доступны всегда (мессенджеры/заметки).<br />**Комментарий:** это минимальный уровень, чтобы MVP можно было использовать в быту.|
|NFR-08|Надёжность|Сессии без сбоев|Доля сессий без сбоев ≥ 99%.|Must|**Риск:** частые падения = пользователь не может выполнить действия тогда, когда ему нужно.<br />**Последствия:** рост отказов от продукта, негативные отзывы, падение удержания.<br />**Комментарий:** критично для мобильного приложения, где ценность в быстром использовании.|
|NFR-09|Надёжность|Резервное копирование|Резервное копирование БД выполняется ежедневно; хранение резервных копий - 30 дней.|Should|**Риск:** потеря данных.<br />**Последствия:** потеря данных - продукт теряет доверие.<br />**Расчёт/логика:** ежедневный бэкап задаёт допустимую RPO до 24 часов при разумной стоимости и сложности для MVP.|
|NFR-10|Наблюдаемость|Логирование критичных операций|Логируются критичные операции: создание пространства; генерация кода приглашения; присоединение по коду; создание/выполнение задач; изменения списка покупок; создание/изменение событий календаря.|Should|**Данные:** логирование ключевых событий позволяет быстрее диагностировать и устранять сбои и разбирать спорные ситуации пользователей.|
|NFR-11|Наблюдаемость|Мониторинг и алерты|Система собирает метрики: доступность, время отклика, доля ошибок; настроены алерты при выходе показателей за пороги.|Should|**Риск:** команда узнаёт о проблемах только от пользователей.<br />**Последствия:** простой сервиса, рост ошибок, падение доверия пользователей.|
|NFR-12|Совместимость|Поддержка Android|MVP поддерживает Android 11+.|Must|**Риск:** поддержка слишком старых версий Android повышает риски нестабильности.<br />**Последствия:** затягивание сроков MVP или ухудшение качества из-за распыления усилий.|
|NFR-13|Удобство|Быстрое добавление сущностей|Добавление задачи и добавление покупки выполняется не более чем за 4 пользовательских действия (после открытия пространства).|Should|**Риск:** если добавление занимает много шагов, пользователь поленится фиксировать дела/покупки в момент возникновения потребности.<br />**Последствия:** падение активности, провал активации и удержания.<br />**Комментарий:** достижимо за счёт быстрых действий в интерфейсе (например, кнопка "+" в пространстве и краткая форма создания).|
|NFR-14|Емкость|Емкость пилота по пространствам и активности|Система поддерживает пилот: не менее 300 созданных пространств, где не менее 50% - активные.|Should|**Что измеряем:** “ёмкость” здесь = объём объектов и операций, который система должна выдержать в рамках пилота без деградации доступности и времени отклика.<br />**Риск:** при достижении целевых объёмов пилота начнутся тормоза/сбои и цели пилота станут недостижимы.|
|NFR-15|Масштабируемость|Возможность горизонтального масштабирования backend|Backend должен поддерживать горизонтальное масштабирование (возможность запуска нескольких экземпляров сервиса за балансировщиком) без изменений мобильного клиента.|Could|**Риск:** если backend не масштабируем, то при росте аудитории придётся менять архитектуру под нагрузку.<br />**Комментарий:** для MVP не сильно критично, но снижает риск проблем при более успешном пилоте, нежели требуется для измерения его успешности.|

"**Поддерживаемость"** не включена в  НФТ для MVP:

- **Почему не критична для MVP:** на этапе MVP приоритет - быстрая проверка ценности продукта; строгие требования к поддерживаемости увеличивают сроки и бюджет разработки, не влияя напрямую на проверку гипотез MVP.

- **Риски игнорирования:** 
    - Рост технического долга**:** накопление "быстрых" решений, которые экономят время сейчас, но делают изменения дороже позже (например: отсутствие тестов, плохая структура кода, ручные релизы, недостаток логирования/документации).
    - Замедление развития**:** новые фичи/версии внедряются дольше, потому что повышается риск сломать существующее, больше времени уходит на ручные проверки и исправления.
    - Рост дефектов**:** без автоматических проверок и стандартизации релизов увеличивается вероятность регрессий.

- **План на будущие версии:** добавить требования по поддерживаемости начиная с версии 1.1-1.2, например:
    - минимальный набор автотестов на критические сценарии;
    - стандартизация релизов;
    - базовые правила качества кода.
